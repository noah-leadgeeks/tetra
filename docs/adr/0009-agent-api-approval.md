# ADR-0009: Agent API with Scoped Tokens and In-App Delete Approval

## Status
Accepted

## Context
The user wants a personal agent (OpenClaw, driven by `docs/openclaw/tetra/SKILL.md`) to read and change TETRA data over HTTP: tasks, time entries, calendar events, attendance and breaks. Every existing `/api/*` route relies on the NextAuth session cookie, and `auth()` returns a synthetic session when `DISABLE_AUTH` is on. Destructive actions by an agent must not happen without the user, in line with ADR-0005 (user confirmation before authoritative changes).

## Decision
1. **Bearer tokens stored in the database.** Tokens live in `api_tokens` as sha256 hashes with a display prefix, scopes, optional expiry, `revoked_at` and a throttled `last_used_at`. The plaintext (`tetra_...`) is shown once at creation in Settings → Agent access and is never logged or stored in audit rows. Lookup compares hashes with a length check and `timingSafeEqual`. Scopes are `read` (the default), `write` and `delete`; `write` and `delete` each imply `read`. A single env-var token was rejected: it cannot be revoked without a redeploy, cannot be scoped, is not tied to a user and leaves no usage trail.
2. **Separate namespace.** The agent uses `/api/agent/*` with `withAgentAuth(scope, handler)` and no cookie fallback; the UI routes stay cookie-only. Both call the same domain services. Dual auth on the existing routes was rejected because it would turn every UI `DELETE` into an immediate agent delete and make the `DISABLE_AUTH` bypass reachable with a bearer header.
3. **Hybrid approval.** Reads apply without approval and are not audited. Creates and updates apply directly; the agent confirms with the user in chat first (not enforced by TETRA). Deletes are enforced server-side as pending actions: `DELETE /api/agent/...` only inserts a `pending` row in `agent_actions` (202) and nothing is deleted until the user approves it in `/settings/agent`. The bell shows an `agent_approval` alert linking there.
4. **One table, explicit state machine.** `agent_actions` is both the audit log of agent writes (`executed` / `failed`) and the approval queue: `pending → executing → executed | failed`, `pending → rejected`, `pending → expired`. Approval claims `pending → executing` atomically and marks the row `executed` right after the delete succeeds. A partial unique index allows one `pending` row per target. Pending rows expire after 24 h by default (the agent may request less, at most 1440 minutes); `executing` rows claimed more than 5 minutes ago become `failed` with `timeout`. Expiry is swept lazily on list, poll, approve, reject and notification fetch; there is no cron. Revoking a token expires its pending rows (`token_revoked`). Result codes are fixed: `gone`, `stale`, `timeout`, `token_revoked`, `expired`, `execution_error`, `sync_error`.
5. **Staleness check.** Each pending row stores a fingerprint of the target at request time. The approval card shows the live impact and a "Changed since request" warning, and Approve sends the live fingerprint the user saw as `expectedFingerprint`. The server re-reads the target after claiming and fails the action as `stale` if it no longer matches, or `gone` if the target disappeared. Tasks have no `updated_at`, so their fingerprint is name, completed minutes and the running entry; edits that change only description, priority or due date are not detected (the delete impact is unchanged). Calendar fingerprints cover title, times, all-day, Google event id, `sendUpdates` and guest count (so a change in who gets notified makes the card stale), and exclude `updated_at` and `html_link`, which every Google import bumps.
6. **Sheet sync after agent writes.** Agent entry, break and timer-stop writes, and approved time-entry and break deletes, sync the affected days through `syncDaysAfterChange` with the same gating as Timeline auto-sync (`autoSyncTasks`, active config, not file mode), sequentially under a 20 s budget. **Approved task deletes never auto-sync**, matching `DELETE /api/tasks/:id` in the UI: the affected days stay `changed_after_sync`, show "Not synced", and are reported to the agent as `result.needsSync`. Calendar writes never touch the sheet.
7. **No agent access under `DISABLE_AUTH`.** While `DISABLE_AUTH` or `NEXT_PUBLIC_DISABLE_AUTH` is on, every `/api/agent/*` request, token management, delete requests and approve/reject return 403 `auth_bypass`. `isAuthBypassActive()` in `src/server/auth.ts` is the single definition of the bypass check.
8. **`ALLOW_DEV_LOGIN` is development only.** With dev login on, anyone who can reach the app can sign in as any email, create a token and approve deletes for that user. It is not blocked (Playwright e2e signs in through it) but must be off in production; `/settings/agent` shows a warning banner while it is on.
9. **Calendar writes need `calendar.events`.** Google sign-in now requests `https://www.googleapis.com/auth/calendar.events` in addition to `calendar.readonly`, and records the granted scopes on `users.google_scopes`. Calendar services attempt Google writes only when that scope (or `calendar`) was granted, and return an explicit `google: { synced, error }` (`missing_scope`, `not_linked` or the Google message) instead of failing silently. This requires adding the sensitive scope to the OAuth consent screen in the Google Cloud console (re-submitting verification if the app is published) and a one-time sign-out/sign-in per user.

### Exception to ADR-0004
`autoSyncAfterClose`, shared by `POST /api/attendance/stop`, the attendance edit route and the agent clock-out / attendance routes, calls `setReviewed` and syncs the day **without a human review step**. This is pre-existing behavior of the clock-out routes, now also reachable by the agent. It is a documented exception to ADR-0004 (explicit review before sync), gated by `autoSyncOnClockOut`; on failure the day is reset to `draft` (clock-out) or `ready` (attendance edit) and a failed sync never fails the clock-out itself.

## Consequences
- The agent can do everything the UI can except delete without the user; every agent write and decision leaves a row in `agent_actions`, visible in Settings → Agent access → Recent agent activity.
- Bearer tokens carry the same read/write power as a session, so a leaked `write` token can change data until revoked. Mitigations: hashed storage, `read`-only default, revocation, optional expiry, `last_used_at`, and no immediate deletes.
- Migration 0008 is additive (one enum, two tables, one nullable column, one partial unique index) and must be applied before the code that selects `users.google_scopes` is deployed; rollback is code first, then the manual down statements at the top of `drizzle/0008_agent_api.sql`.
- Agent writes can update the official Google Sheet without a human present at the moment of the write (same gating as UI auto-sync). Task deletes leave days marked "Not synced" until the user syncs them.
- No rate limiting is implemented (single personal user); the skill asks the agent not to poll faster than every 15 s.
